# 项目审查（2026-10-28）

审查基线：`7c938f5`，审查前工作区干净。范围包括交接、作业原文、规格、全部生产 Swift 文件、单元/集成/UI 测试、工程配置、生成器、CI 和报告。此次只交付审查与证据，不修复生产代码、不提交 Git。

结论：正常路径已具备可复现的基础，但现有绿灯不足以证明确定性验收全部完成。保存失败被当成成功、原图查看入口缺失、编辑后的 vCard 过期，都能直接影响核心闭环。参考 App 的行为等价仍缺证据；这应当作为交付阻塞项处理。

## 一、功能与数据问题

### R01 [P1] 持久化失败仍返回保存成功，删除失败还会丢图片

位置：`Sources/Persistence/CardLibraryModel.swift:68–99,149–155`；`Sources/Features/Scanner/ScanFlowModel.swift:138–156`；详情编辑也调用同一个不抛错的 update。

add/update/delete 先修改内存，再调用会吞掉错误的 persist。ScanFlowModel.save 得到非空 BusinessCard 后，确认页直接关闭。lastErrorMessage 没有任何 UI 使用；磁盘写入失败时，用户看到的是成功。重新启动会丢失新名片或编辑内容。

直接用项目原始类型和一个 save 抛错的 CardStore 复现：`returned=true, flowError=nil, inMemory=1, disk=0`。删除探针的结果为 `diskCards=1, imageExists=false`：图片先删除，JSON 更新失败，重启后记录仍在但原图永久丢失。

建议：让写入结果传播到调用方；持久化成功后才提交内存状态/退出页面；删除先提交记录，再清理图片；保存失败应回滚已写图片或在之后清理。补充失败 store 的新增、编辑、删除回归测试，并断言重建 store 后的数据和图片。

### R02 [P2] 查看原始图片的界面存在，但用户无法打开

位置：`Sources/Features/Detail/CardDetailView.swift:14,52–56,164–172`。

showImageViewer 从未设为 true；cardImage 只显示 Image，没有 Button 或点击手势。因此正常保存包含两张图的名片后，点击缩略图不能进入 CardImageViewer，也无法切换原图。规格 10.2.1、作业“查看原始名片”和交接中的“已补”不成立。

建议：给缩略图接入可访问的按钮，补充“扫描保存→详情→打开图片→切原图”的 UI 测试。现有 T13 只断言公司文字，没有检查图片操作。

### R03 [P2] 详情编辑后立即导出的 vCard 仍是旧数据

位置：`Sources/Features/Detail/CardDetailView.swift:57–59,245–254,264–269`。

vCard 只由 `.task(id: cardID)` 生成。编辑保持同一 UUID，saveEdits 更新记录但没有重建导出文件。姓名、公司、号码等改完后，在同一详情页导出仍分享旧值；退出重新进入才会刷新。

电脑操作复现：用 zh-01 扫描并保存到内存测试库，进入详情，将公司改为 Review Company 并保存。可访问性树显示新公司，容器内待分享 VCF 却与编辑前逐字节相同，ORG 仍为同济大学。[手动验证证据](review-evidence-2026-10-28/stale-export.txt)。

建议：在分享时从最新记录生成，或绑定记录修订刷新；文件名用 UUID 避免同名联系人覆盖。验证“进入详情→编辑→导出”，读取实际 VCF 内容，而不只测 exporter 的纯映射。

### R04 [P2] 边界检测的长宽比参数不符合 Vision API

位置：`Sources/Services/Recognition/VisionCardDetector.swift:12–14,31–33`。

规格的 1.25–2.4 是长边/短边；Vision 接收短边/长边，合法范围 0–1。应转换为约 0.417–0.8。本机探针设置 1.25/2.4 后读回 0.5/1.0：当前运行时静默忽略无效最小值并钳制最大值。因此测试图片能检出，不代表规格的比例筛选生效：方形也可进入候选，比例 2.0–2.4 的卡片反而可能被排除。

依据：[Apple minimumAspectRatio](https://developer.apple.com/documentation/vision/vndetectrectanglesrequest/minimumaspectratio)、[maximumAspectRatio](https://developer.apple.com/documentation/vision/vndetectrectanglesrequest/maximumaspectratio)。探针运行于 macOS Vision；iOS 应补测具体参数行为，不应依赖无效值的静默处理。

建议：在服务边界转换比例，补方形干扰物和宽名片的正反例，而不只断言两个 fixture 返回非 nil。

### R05 [P2] 同一行多个电话标签会全部使用第一个标签

位置：`Sources/Services/Parsing/PhoneClassifier.swift:37–39,60–67`。

输入 `Mobile: 13800001234 Tel: 021-60001234 Fax: 021-60005678` 时，三个号码均被标为 mobile，置信度均为 0.96。分类器只拆一次行首标签，再用于整行所有号码。OCR 将同一行读成一个 observation 是正常输入形态。

建议：按每个号码最近的标签分类。保留现有“Tel 标签对应斜杠分隔的两个同类号码”测试，再补同一行混合标签测试。这个问题不同于文档明确接受的“无标签号码无法分类”。

### R06 [P2] 邮箱里的数字会被虚构为电话号码

位置：`Sources/Services/Parsing/PhoneClassifier.swift:41–68`；`Sources/Services/Parsing/BusinessCardFieldParser.swift` 的 prepare 阶段。

输入只有 `Jordan Lee / Designer / Email: user13800001234@demo.example`，项目原解析器同时产生手机 `13800001234`，置信度 0.88。号码扫描没有排除邮箱/网址已占用的字符区间，也没有 token 边界。已有 testEmailDigitsAreNotAPhone 仅用两位数字，未覆盖能通过号码长度门槛的邮箱。

建议：先屏蔽邮箱/网址区间，再提取号码；补充纯数字邮箱用户部分、网站路径、地址数字等反例。这是“不存在的信息不得填”的直接反例，不能用当前的幻觉率 0% 排除。

### R07 [P2] 网址正则可以截断成另一个有效域名

位置：`Sources/Services/Parsing/KeywordTables.swift:96–99`。

`www.example.com.hk` 被解析成 `www.example.com`；由于白名单 TLD 后没有域名结束边界，匹配部分成功后，不再走完整 www 前缀兜底。用户点击/导出可能访问另一个站点。

建议：识别完整 host 再验证，不允许在点或域名字符中间结束。正则测试需要比较完整匹配值，而不只是 firstMatch 非空；补多段后缀和以白名单项开头的新后缀。

### R08 [P2] 标签大小写去重与附加/筛选语义不一致

位置：`Sources/Features/Shared/TagPickerView.swift:74–79`；`Sources/Persistence/CardLibraryModel.swift` 的 ensureTag、cards(matching:tag:)。

已有 Conference 时新建 conference，ensureTag 返回已有标签，但调用方忽略返回的规范名称，把小写字符串附加到草稿。库只有 Conference，名片保存 conference，筛选使用大小写敏感 contains。探针确认：库标签 `[Conference]`、名片标签 `[conference]`、筛选 Conference 得 0 条；删除规范标签也无法清掉小写引用。

建议：使用 ensureTag 返回的规范名称，并在统一写入口规范化全部标签。补“大小写不同的附加→筛选→删除→重启”的完整测试。

### R09 [P2] 列表左滑删除绕过二次确认

位置：`Sources/Features/CardList/CardListView.swift:112–118`。

详情删除有 confirmationDialog，列表 `.onDelete` 却直接调用 library.delete，立即删除记录和图片。规格 10.4 要求删除需二次确认，并未豁免列表入口。当前 T17 只测详情路径，遗漏这一入口。

建议：两个入口统一走待删除记录和确认流程；补左滑删除后点取消/确认的 UI 测试。

### R10 [P2] 确认页“取消”与规格不符，创建标签还会提前写入

位置：`Sources/Features/Scanner/ScannerFlowView.swift:33–38`；`Sources/Features/Scanner/ScanFlowModel.swift:132–134`；`Sources/Features/Shared/TagPickerView.swift:74–79`。

规格 9.4/7.2.5 要求取消返回名片夹且无写入。确认页取消实际 retake 回到取景，必须再点一次取消；现有 T20 恰好把“两次取消”写成预期，证明的是实现自洽。另在确认页新建标签立即 ensureTag→persist，即使最终取消，标签仍保留。编辑表单中的全局删除标签也立即影响全部名片，取消编辑不会撤销。

建议：明确表单草稿与全库标签管理的提交边界；确认页取消应退出流程；新增标签在保存时提交。分别验证取消后的卡片数、标签库和已有卡片标签。

### R11 [P2] OCR 失败回裁剪页，但错误原因没有展示

位置：`Sources/Features/Scanner/ScanFlowModel.swift:126–129`；`Sources/Features/Crop/CropView.swift`。

recognize 抛错时只设置 errorMessage 并切回 crop。CropView 从未显示该值；只有 ScannerView 显示 errorMessage，而 retake 又清掉它。用户点击下一步失败后看到原页面，无从知道失败或如何恢复。规格 7.4.3/异常表要求明确提示。

建议：在裁剪/流程容器展示错误与重试/重拍入口；用抛错 recognizer 验证，而不只测取消和空文本。

### R12 [P2] async 识别函数没有让出主线程，处理态和取消无法正常响应

位置：`Sources/Features/Scanner/ScanFlowModel.swift:102–125`，类被标为 MainActor；confirmPreview 也同步检测。

confirmCrop 内从设置 processing 到设置 review，所有调用都是同步的，没有 await。Vision perform、Core Image 和 parser 全部占用主 actor；正常识别耗时内，ProgressView 可能来不及绘制/动画，取消也不能响应。函数声明 async 本身不会把工作移到后台。真实大照片比 fixture 更容易放大这个问题。

建议：把检测、校正、OCR 放到受控后台执行单元，只在主 actor 提交状态；加入取消/过期结果保护。用耗时 recognizer 测主 actor 心跳及取消，再用真机照片测峰值内存与响应。

### R14 [P1，证据] 当前准确率/幻觉率不足以覆盖图像到字段和完整集合

位置：`Tests/Integration/ParserBenchmarkTests.swift:47–107,148–190`；`Tests/Integration/VisionOCRTests.swift:64,79–89`。

文本基准由 GT 按固定姓名最大、固定行顺序拼造，不保留各图片版式。这个边界报告主体已说明，问题是实际图像链路只对少量 fixture 断言姓名非空；公司、职位、所有号码/邮箱/网址等只打印，并不对 GT 断言。

此外，文本基准只比较首个邮箱、每类首个号码，额外/漏掉的后续值不能被发现；expected_absent 只检查 website/company。实际 flat 语料没有缺公司样本，15 次 no_hallucination 全是缺网站；13 张缺地址与16张缺部门没有纳入。因而不能据此推出所有字段的幻觉率为 0，也不能证明多值字段全正确。Vision 的所谓 character recall 实际是整条 present_text 是否被包含的平均占比，命名和报告须说清。

建议：保留理想文本单测；另对全部固定图片真实运行检测/校正/OCR/解析，与 GT 比较完整集合。逐类记录缺失、错值、额外值；按语言/版式/照片/遮挡切片，不修改原有通过门槛来迎合结果。

### R15 [P2，交付] 保存后无法恢复人工修改前的结构化识别结果

位置：`Sources/Models/BusinessCard.swift`、`Sources/Models/CardDraft.swift`；规格数据模型明确中间产物不持久化。

BusinessCard 仅存 rawText 和最终手改字段；原 ParsedCard、字段 evidence/confidence、OCR 逐行坐标/置信度不保存，离开流程即丢失。无法在重启后重建作业要求的“Structured Fields→Manual Correction→Final Contact”证据，详情原文页也传入空 lines。

建议：作为旁路实验记录/识别快照保存，不必重写 CardStore 或引入数据库；保留原始识别与最终记录的关联，能够导出前后差异。现有规格与作业要求需要同步澄清。

### R16 [P2，语料] 字体池是回退列表，不是字体覆盖

位置：`Scripts/generate_test_cards.py:151–158,237–241`。

所有卡、所有字号都调用同一 FONT_CANDIDATES，pick_font 永远选第一个可用字体。FONT_SANS/SERIF/MONO 没有参与渲染。因此“用了3种字体”也不准确；同一机器通常只用一个字体族，仅字号不同。扩大候选数组仍只增加回退，不增加覆盖。

建议：按 card id/版式确定性选择不同字体族，写入 manifest，再另行授权变更语料并重跑。此次没有重生成或改动语料。

### R17 [P2，工具] 首次运行命令构建目录与安装目录不一致

位置：`Makefile:6,41,45–50`。

XCODEBUILD 未指定 derivedDataPath，产物在 Xcode 默认 DerivedData；APP_PATH 却固定为 build/Build/Products。干净仓库执行 make run 会编译成功但找不到待安装 App；若目录残留，可能安装旧构建。当前 make verify 日志确实写入默认 DerivedData。reset 也复用同一错误路径。

建议：统一 derivedDataPath 或从 build settings 取得实际产品路径，并在干净输出目录验证首次运行。不要为演示而依赖之前跑过 Scripts/verify.sh 产生的目录。
