## 2. 业务任务与用户可见流程

用户从名片夹进入扫描，取得一张照片，确认照片质量，调整名片边界，执行识别与字段解析，核对内容并保存。保存后可以再次查看、编辑、搜索、添加标签、记录备注、删除和导出。该流程围绕一张具有稳定标识的名片记录展开。

### 2.1 拍摄与导入

相机拍摄进入照片预览，用户通过“重拍”和“使用这张”决定是否继续。预览页用于检查照片内容，裁剪页显示四角与校正范围。相册导入完成图片加载后进入裁剪，使用同一套检测、校正、识别、解析和保存逻辑。

扫描过程中可以取消。取消使当前操作标识失效，已在后台执行的结果返回时需要通过标识检查。扫描表单未保存时，名片记录及草稿标签保持未提交状态。用户重新选择图片、重拍或退出后，旧任务完成不能改变新的草稿。

### 2.2 确认与保存

OCR 结果显示为可编辑字段，用户能够修正姓名、公司、职位、电话、邮箱、网站和地址。多个号码保留各自类型，多个邮箱保留独立条目。未归类文字提供人工核对来源，初始解析及其证据随识别快照保存。

姓名为空时保存按钮禁用。保存成功关闭扫描流程，列表立即显示新记录；写入失败保留表单，显示失败原因，并允许用户处理后重新提交。用户看到的关闭动作与实际写入结果保持对应关系。

### 2.3 记录管理

列表显示姓名、公司与职位、首个号码、标签和缩略信息。进入详情可以查看字段及图片，在原图和校正图之间切换。编辑后的内容重新提交至文件库，并更新修改时间。搜索支持姓名、公司、职位、电话和邮箱，标签提供独立筛选条件。

| 用户动作 | 可见结果 | 数据要求 |
|---|---|---|
| 新增并保存 | 返回列表，新名片出现 | 图片与结构化记录可以重新读取 |
| 编辑并保存 | 详情显示修改值 | 更新同一 id 的记录 |
| 取消编辑 | 返回已有内容 | 草稿修改不提交 |
| 删除并确认 | 名片从列表消失 | JSON 提交后清理无引用图片 |
| 取消删除 | 名片仍可查看 | 原有记录及图片保持 |
| 终止并重新启动 | 找到原有名片与修改 | 从持久化文件恢复 |
| 导出 VCF | 获取标准联系人文件 | 使用当前已保存的字段 |

## 5. 模块职责与协议设计

项目按领域模型、服务、持久化、功能界面和支持工具组织代码。界面通过装配后的服务访问能力，模型和状态逻辑依赖协议。相机、检测、识别、校正、解析、导出和存储具有明确输入输出。

```mermaid
flowchart TD
    A[相机或相册] --> B[ImageCoding 归一方向]
    B --> C[ScanFlowModel]
    C --> D[CardDetecting 与四角调整]
    D --> E[ImageCorrecting]
    E --> F[TextRecognizing]
    F --> G[FieldParsing]
    G --> H[CardDraft 与 ReviewView]
    H --> I[CardLibraryModel]
    I --> J[CardStore JSON 与图片]
    I --> K[详情、搜索、标签和导出]
```

### 5.1 服务接口

| 协议 | 输入 | 输出及失败语义 |
|---|---|---|
| CardDetecting | CGImage、方向 | Quad 或没有检测结果，允许整图继续 |
| ImageCorrecting | 图片及四角 | 校正后的图片；失败由流程提供恢复路径 |
| TextRecognizing | 实际识别输入、方向 | OCRResult；识别异常向调用者传播 |
| FieldParsing | OCRResult | ParsedCard，字段含值、置信度与依据 |
| ContactExporting | BusinessCard | VCF 数据或通讯录写入结果 |
| CameraPermissionProviding | 当前权限或请求动作 | 显式权限状态 |
| CardStore | 库与图片读写 | 加载值或抛出可显示的错误 |

AppServices.make 是依赖装配位置。生产配置创建系统服务；测试配置可以改变权限状态、存储类型、错误注入和图源。固定图源影响图片获取入口，检测、Vision 和规则解析仍由相应具体实现执行。

### 5.2 状态与并发

界面状态通过 @Observable 在主 actor 发布。AVCaptureSession 使用专门队列启动和停止。检测、透视校正、OCR 与字段解析在后台任务执行，结果返回时检查 operationID。相册加载也使用同一失效机制。

取消任务后，底层识别调用可能已经开始执行。状态安全由结果有效性检查保证：当前标识已经改变时，返回的值和错误均被忽略。测试同时检查界面能够响应取消，以及迟到结果保持失效。

### 5.3 设计决策材料

ADR-0001 记录 Vision 与 Core Image 选型；ADR-0002 记录规则解析；ADR-0003 记录文件持久化；ADR-0004 记录协议与固定测试图源；ADR-0005 记录工程生成与提交格式；ADR-0006 记录识别快照、完整测量与证据规则。具体文件见 [架构目录](../architecture/overview.md)。

## 6. 领域模型、草稿与时间语义

BusinessCard 代表保存后的名片，id 用于列表导航、更新和导出隔离。字段包含姓名、公司、职位、部门、电话集合、邮箱集合、网站、地址、标签、备注、图片标识、识别原文、识别快照和创建/修改时间。

### 6.1 字段表示

可选字符串允许为空，多电话和多邮箱采用数组。每个电话号码具有 kind 与 number，kind 为 mobile、office 或 fax。相同号码在不同明确类型下分别保留，同一类型内按数字去重。此规则允许名片上电话和传真使用同号的情况。

| 字段组 | 数据形式 | 具体用途 |
|---|---|---|
| 身份和排序 | UUID、createdAt、updatedAt | 定位记录，按修改时间排序 |
| 基础联系人 | String 与 String? | 姓名、公司、职位、部门、网址和地址 |
| 多值联系方式 | PhoneNumber 数组、邮箱数组 | 保留全部号码、类型和邮箱 |
| 管理信息 | 标签数组、备注 | 筛选、检索与补充记录 |
| 图像 | originalImageID、processedImageID | 找到独立图片文件 |
| 识别证据 | rawText、RecognitionSnapshot | 核对初始识别与后续修改 |

### 6.2 编辑草稿

CardDraft 用于确认页面和详情编辑。表单在草稿中增删电话和邮箱，保存时过滤空内容，并生成 BusinessCard。姓名的非空要求由 canSave 表达，字段是否存在由实际内容和用户确认决定。

标签新增和删除操作同样暂存草稿。取消表单会丢弃这些操作；保存时将名片变更与标签变更一次提交。全库标签删除需要同时从其他名片上移除，事务候选库用于保持记录一致。

### 6.3 初始快照与最终记录

RecognitionSnapshot 保存 OCRResult 与最初的 ParsedCard。之后修改姓名或公司会更新最终字段，初始快照继续保存第一次识别信息。RecognitionSnapshotTests 验证人工修改、再次编辑、写入和重新读取后的快照内容。旧 JSON 缺少 recognition 时仍可解码。

创建时间保留记录的初始时间，修改时间在实际提交时更新。搜索列表按 updatedAt 排序，修改后记录可以出现在较前位置。时间由可注入的 now 提供，测试能够稳定断言排序和提交结果。

## 7. 文件存储、提交顺序与恢复

文件库位于 App 的 Application Support/CamCardReplica。library.json 保存结构化记录，Images 目录保存按 UUID 命名的 JPEG 文件。JSON 采用可读缩进、稳定键排序和 ISO-8601 日期，便于检查具体字段与图片引用。

```text
CamCardReplica/
  library.json
  Images/
    <original-image-id>.jpg
    <processed-image-id>.jpg
```

### 7.1 新增记录

新增时生成两张图片的独立标识，写入图片文件，构造包含图片引用的候选记录及候选库。CardLibraryModel.commit 调用 CardStore.save，成功后发布 cards 和 tags。任何图片或 JSON 写入失败都会传播错误，新增路径清理本次已经写入的图片。

这条顺序使确认页面的关闭与 JSON 提交结果对应。失败时，用户可以继续检查表单、修改内容或重新保存；内存中的已提交库保持原有值。针对第二张图片写入失败、JSON 保存失败和重试成功均有测试。

### 7.2 编辑、标签和删除

编辑构建候选数组并替换相同 id 的元素，更新 updatedAt 后提交。标签标准化会去除空白、合并大小写不同的名称、去重并排序。删除动作先提交剩余记录，再计算仍被引用的图片集合，只删除已经没有引用的文件。

图片和 JSON 分别写入。进程如果在 JSON 已提交、旧图片尚未清理时终止，可能留下无引用图片；已提交记录的图片保持引用关系。该文件级边界在 ADR-0003 中记录，测试覆盖可控制的失败位置。

### 7.3 加载失败

文件不存在时返回空库；文件存在且无法解码时返回读取错误。CardLibraryModel 区分 loadError 与操作错误，加载恢复前拒绝提交候选库。首页显示原因和“重试”，避免用户在未知读取状态下继续创建记录。

重试调用 reload 重新读取原文件，成功后发布实际库并清除错误。测试检查读取失败、原文件保持、重新读取和恢复扫描入口。取消或失败不会自动创建一份空文件替换旧库。

### 7.4 重新启动证据

T18 使用独立 UUID 文件库运行：保存修改、标签、备注和图片，终止 App，重新启动，再打开同一记录检查姓名、公司、备注、标签以及原图/校正图。该 UI 用例执行实际 terminate/launch，文件库单元测试另行完整回读。

## 8. 相机、相册与 FauxCam 验证

CameraController 封装 AVCaptureSession、AVCapturePhotoOutput、会话队列与照片代理。配置时发现后置广角设备，创建 AVCaptureDeviceInput，将输入与照片输出加入会话。拍摄通过照片代理异步返回图像 Data，后续解码和流程转换由界面及模型完成。

### 8.1 权限状态

SystemCameraPermission 将系统状态转换为应用状态，只有 authorized 允许使用快门。首次请求、拒绝状态映射和界面禁用行为具有单元及注入 UI 测试。Xcode 模拟器专项使用真实系统服务完成已有授权、已有拒绝、首次弹窗允许及首次弹窗拒绝四项检查，全部通过，并保存系统弹窗截图。实际设备上的设置返回未验证，详见 [权限证据](evidence/permissions-2026-11-07/README.md)。

相册通过 PhotosPicker 提供选择结果，加载在异步入口完成。选择取消、空数据、损坏图片和加载错误具有明确处理。2026-10-28 已保存实际系统 PhotosPicker 的选取和取消截图。

### 8.2 固定图源与外部输入

常规 UI 回归使用 fixture-camera 启动配置，方便稳定检查预览、裁剪和后续表单。FauxCam 专项将 fixture-camera 设为 NO，使用实际快门按钮和正常 AVCapturePhotoOutput 回调取得图片。

本次从 [官方 FauxCam 发布页](https://github.com/mkemalgokce/fauxcam/releases/tag/v1.1.0)下载 v1.1.0 应用与对应 CLI，核对发布文件 SHA-256。应用安装在用户 Applications 目录，CLI 安装在用户 .local/bin。工具本体和动态库保留在本机，仓库保存测试代码、复现命令、截图及日志。

### 8.3 专项条件与记录

## 9. 名片边界、坐标与透视处理

自动检测使用 VNDetectRectanglesRequest。配置将名片长边/短边比例限制在 1.25–2.4，最小尺寸为 0.15，角度容差为 35，最多保留三个候选，并按照 0.75、0.55、0.35 的置信度逐次尝试。

### 9.1 比例与候选选择

Vision 使用短边/长边比例，因此传入区间为 1/2.4 到 1/1.25。候选四边形经过面积和坐标检查后选择面积最大的对象。检测失败返回没有结果，由流程采用整图边界继续。

Quad 保存左上、右上、右下、左下四个角，坐标归一化为 0–1。面积使用四边形顶点计算，拖动后的坐标限制在图片范围。测试覆盖宽卡、方形、坐标钳制、透视输入和单个角被遮挡的情况。

### 9.2 坐标系转换

Vision 的原点位于左下角，界面和模型约定原点位于左上角。检测适配层执行 y = 1 - y；透视校正将归一化坐标乘以图片宽高，并转换回 Core Image 所用的纵向坐标。所有角点按同一顺序传入 CIPerspectiveCorrection。

照片进入流程时将 EXIF 方向应用到像素。检测、校正和 OCR 因而处理同一方向与坐标。图像方向测试检查旋转后宽高与像素位置，避免四角来自一个方向、图像使用另一个方向。

### 9.3 整图与错误恢复

quad 等于 fullFrame 时直接返回方向归一后的输入。R25 的像素回归发现，即使透视变换几何上保持整图，重采样与颜色处理仍可能改变小字像素，因此整图路径保留原始解码像素。

透视处理失败时使用输入图继续识别，识别失败则返回裁剪页面显示原因。用户可以重新调整或重拍。合成照片中的透视、阴影和遮挡提供固定回归输入，真实拍照条件由作者补充。

## 10. Vision 输出、阅读顺序与证据结构

文字识别采用 VNRecognizeTextRequest，level 为 accurate，语言为 zh-Hans 与 en-US，启用语言纠正，minimumTextHeight 为 0.008。请求使用实际校正图或整图输入，OCRResult 同时记录图片尺寸和处理耗时。

### 10.1 逐行数据

每个 Vision 观察保存第一候选文字、置信度和矩形。矩形转换到左上角原点后用于后续布局判断。rawText 按纵向位置排序并以换行拼接；ParsedCard 使用的 readingOrderedLines 会进一步将相近纵向位置视为同一行，并按横向位置排序。

这一区别影响两栏名片：原文用于保存观察内容，字段解析还需要结合相邻行、字号线索和位置。OCR 原文中可能存在重复标签或字符误识别，后续解析会进行文本归一与分类，原始观察继续保留。

### 10.2 置信度的含义

Vision 的逐行置信度随候选文字保存。ParsedValue 的置信度来自规则评分，两者在数据结构中分别记录。界面低置信提示使用解析候选值，不能从单个平均值确定整张名片是否全部正确。

本批数据包含邮箱字符错误和电话类型歧义。即使某些字段具有较高评分，用户仍需要核对原图与字段。报告通过逐图对 GT 测量记录实际错误，界面通过人工确认控制最终保存值。

### 10.3 原始证据附件

批量测试对每张图片记录 sourceSHA256、processedImageFile、processedImageSHA256、检测四角、处理方式、OCRResult、ParsedCard 和字段比较。实际识别输入编码为 PNG，作为 XCTest 永久附件保存。

导出工具从同一 xcresult 读取图片附件，按照 SHA-256 匹配记录，校验源图与 GT，再导出原文、初始字段、图片及统计。run.json 保存日期、设备、结果包、识别配置、GT 哈希和测量时 Swift 源文件哈希。具体文件说明见 [OCR 原始证据索引](evidence/ocr-2026-11-07/README.md)。

## 11. 字段解析规则与证据评分

HeuristicFieldParser 接收 OCRResult，输出 ParsedCard。它处理文本归一、阅读顺序、联系方式提取、姓名与组织字段评分、地址证据及低置信过滤。每个候选保存实际值、confidence 和 evidence，方便界面展示和错误追溯。

### 11.1 文本与联系方式保护

TextNormalizer 统一常见标点、标签和文字空白，并为中英文混排提供处理。邮箱和网址使用正则提取；其他分类规则检查文字时屏蔽已经识别的联系方式区间，减少域名中的公司、职位或部门关键词参与评分。

电话号码扫描同样屏蔽邮箱和网址占用范围，防止邮箱用户部分的长数字被当成号码。地址规则排除联系方式中的数字和地址词，避免电话、邮箱及网址构成虚假的邮编或街道证据。

### 11.2 姓名、公司和职位

姓名候选结合文字位置、字号线索、称谓与其他字段特征。公司规则使用机构词表和法律后缀，职位规则扣除机构等冲突证据后要求净分为正。没有合格职位候选时保留空值，防止从负分候选中选取一个结果。

部门字段使用部门词表与组织上下文。原文中存在一行文字，并不保证规则能够正确分配；本次 department 测量保留漏提取情况。用户可以通过未归类文字和原图修正。

### 11.3 电话标签与格式

PhoneClassifier 识别 Mobile、Tel、Fax 及中文标签。同行多个号码根据各自位置关联最近标签。明确标签的候选评分为 0.96。没有标签时依据号码格式提供候选：中国手机格式评分 0.88，区号样式座机评分 0.82，部分服务号码评分 0.78，国际或其他格式使用较低评分。

| 输入依据 | 当前处理 | 保留的风险 |
|---|---|---|
| 明确 Mobile / 手机标签 | 分类为 mobile | OCR 可能识别错误标签或号码 |
| 明确 Tel / 电话标签 | 分类为 office | 标签位置可能受排版影响 |
| 明确 Fax / 传真标签 | 分类为 fax | 标签缺失会削弱依据 |
| 同号、不同明确类型 | 各自保留 | 导出时需保持两个标签 |
| 无标签、区号格式 | 提供 office 候选 | 传真也可能使用同类格式 |
| 无标签、国际格式 | 提供较低置信候选 | 手机与办公电话存在歧义 |

本次 zh-06 的号码被分类为座机，GT 将其定义为传真。号码格式无法提供该类型所需的全部证据，完整集合测量继续记为错误，界面允许人工修改类型。

### 11.4 网站、地址与缺失字段

网站候选需要 www/http(s) 前缀或网站标签。无法确认的裸域名保留为未归类文字。该规则来自邮箱 @ 被 OCR 丢失后误生成网站的回归案例，也会增加部分无标签网址的人工填写工作。

地址可以使用非空 Address/Add/地址标签、门牌号与街道词、行政区和邮编等证据。测试包含短地址、空标签、孤立街道词、联系方式中的数字和复合街道后缀。

低于保留阈值的候选被过滤，界面针对保留的低置信字段显示核对提示。缺失字段测试单独检查没有网站时的输出，完整测量还检查其他字段的缺失误填。规则评分、固定语料统计与人工核对共同提供检查依据。

## 12. 人工确认、草稿取消与保存错误

ReviewView 将识别输出转为 CardDraft，提供字段表单、低置信提示、OCR 原文与未归类文字。用户能够添加、修改和删除号码或邮箱条目，并选择电话号码类型。标签与备注随草稿保留，确认保存时提交。

### 12.1 用户核对内容

用户需要核对字符、字段类别及多值完整性。例如 contact01 与 contactol 的差异涉及字符，office 与 fax 涉及类别，漏掉第二个邮箱涉及集合完整性。这些问题在界面上使用相应文本或类型控件修改，最终保存内容来自确认后的草稿。

OCR 原文弹层显示初始解析结果和依据，并保留逐行置信度。用户可以查看规则为什么选取某个字段，再结合原图确定修改。确认页顶部的置信度是对当前候选评分的汇集，完整性由具体字段核对和测试检查。

### 12.2 空值与修改

空白输入在生成保存记录时归一为空值，空的号码和邮箱不保留。姓名要求非空，这一条件同时用于保存按钮和模型保存入口。OCR 完全没有文字时允许进入空表单，用户填写姓名后可以继续保存。

标签新增与全库标签删除记录在草稿中。确认页面或详情编辑取消后，未提交的标签保持丢弃状态。标签大小写归一化、删除影响其他名片等逻辑通过库模型单元测试检查。

### 12.3 错误反馈

保存失败时页面保留字段，显示错误并允许重新操作。存储异常向模型和界面传播，提交成功后才关闭流程。测试通过失败 store 检查原库、候选记录和图片清理；UI 测试检查保存失败提示与表单保留。

后台识别失败时返回裁剪，用户可以重新调整或重拍。取消后迟到的错误和成功结果均需要通过操作标识检查。相册加载失败和识别失败分别保留原因，避免旧任务错误覆盖正在处理的新图片。

作者实际修改的值、不同字段修改数量、编辑动作次数、操作日期及附件保存在 [人工修改表](../submission/manual-corrections.csv)。这些数据目前由作者填写。

## 13. 名片列表、检索与标签管理

CardLibraryModel 提供按查询和标签过滤后的记录，并按 updatedAt 倒序排序。列表通过记录 id 进入详情，新增或编辑提交后由观察状态刷新。读取失败提供独立错误页面，成功恢复前禁用扫描。

### 13.1 搜索内容与数字归一

BusinessCard.searchableText 包含姓名、公司、职位、部门、地址、备注、网站、号码、邮箱和标签，合并后转换为小写。查询去除首尾空白；空查询返回全部记录。

纯数字和加号形式的查询先提取数字，在电话的数字部分中进行包含匹配。因此保存为带空格或连字符的号码可以通过连续数字查找。其他文本使用归一后字符串包含关系，测试覆盖姓名、公司、职位、电话与邮箱。

### 13.2 标签语义

标签具有名称与用于标识的大小写归一值。创建时去除空白，已有同名标签使用规范名称；给名片附加标签后可以在列表筛选。删除全库标签会从标签集合和所有记录中移除。

筛选与搜索可以组合：先检查标签，再检查查询。测试覆盖标签创建、附加、筛选、大小写和删除后的重新读取。确认或编辑期间的标签变化在草稿中暂存，保存时一次提交。

### 13.3 详情与外部入口

详情显示保存字段和图片。点击图片打开查看器，允许切换原图与校正图；电话号码、邮箱和网站提供系统 URL 入口。删除具有确认步骤，列表左滑删除与详情删除均支持取消。

备注可以用于记录会议、来源和后续联系信息，随记录持久化并参与搜索。它与原始 OCR 文字分别保存，用户备注不覆盖识别证据。详情的当前字段也是导出数据来源。

## 14. 联系人映射、VCF 与导出更新

ContactsExporter 将 BusinessCard 转为 CNMutableContact，再使用 CNContactVCardSerialization 生成 VCF。保存到通讯录时请求系统授权，成功后使用 CNSaveRequest 写入；拒绝或编码失败通过错误返回。

| 名片内容 | 联系人字段或标签 | 处理规则 |
|---|---|---|
| 姓名 | givenName / familyName | 拉丁姓名使用最后一部分作为 familyName；含中文时保留完整姓名 |
| 公司 | organizationName | 空值转换为空字符串 |
| 职位 | jobTitle | 保留当前已保存值 |
| 部门 | departmentName | 按当前字段映射 |
| 手机 | mobile 标签 | 保留每个号码 |
| 座机 | work 标签 | 保留每个号码 |

| 邮箱 | work 标签邮箱集合 | 保留全部邮箱 |
| 网站 | URL 地址 | 必要时补充链接协议用于打开地址 |

VCardDocument 是当前已保存名片的 Transferable 值，分享时生成文件。文件使用 UUID 位置，编辑后导出使用新值，同名联系人的文件相互独立。VCardDocumentTests 修改公司、职位、电话、邮箱、地址和网站后导出，重新解析生成的 VCF 并逐字段断言。

## 16. 合成语料、GT 与样本分布

### 16.2 GT 与缺失信息

每条 GT 包含图片文件名、语言、版式、字体、标签条件、实际字段和缺失字段说明。字段中的多号码具有类型，多邮箱保留全部值。评测加载全部图片并核对文件集合，防止遗漏样本后继续计算。

名片使用虚构姓名、公司、示例域名与固定测试号码。原始图片保持脚本生成结果，测试和文档修改过程中没有手工改变语料图片。生成器的字体选择与文本边界由 Python 工具检查验证。

### 16.3 可复现条件

重建语料需要 Pillow、NumPy 及指定字体。字体缺失时生成器给出错误，font_file 记录实际字体来源。环境和字体变化会影响像素及识别输出，语料版本与测试环境随报告保存。

本次证据补充保持现有语料和 GT。实际识别输入是当次检测/校正后的 PNG，另有对应哈希。原图、处理图、OCR 和字段比较可以按同一个文件名关联。

## 17. 计分口径与字段级结果

完整集合比较对每类字段的全部值进行计分。值去除首尾空白并忽略大小写，电话号码内部格式继续保留。集合中漏掉第二个邮箱或多出一个号码都会导致该字段整项错误。空字符串与空值统一表示缺失。

| 地址 | 25 | 32 | 32 | 43.9% | 43.9% | 43.9% |
| 手机集合 | 75 | 7 | 1 | 91.5% | 98.7% | 94.9% |

## 19. 可靠性修复、AI 协作与能力边界

### 19.1 保存与取消的回归保护

历史审查发现保存失败后的页面关闭、删除失败前清理图片、草稿标签提前提交、原图入口缺失和编辑后导出旧内容等问题。修复通过候选库提交、写入错误传播、图片清理顺序、草稿事务和按当前值生成导出文件处理。

对应测试保留失败 store、第二张图片失败、重试、完整文件回读、删除取消和同名导出隔离。测试断言用户看到的页面与文件内容，异常恢复和正常保存共享同一数据入口。

### 19.2 异步与读取错误

检测、识别和相册加载使用任务标识。替换图片或取消流程后，旧成功与旧错误均不更新当前状态。读取失败与空库分别显示，恢复前禁止写入。异步控制测试、读取失败测试和 UI 重试共同检查这些行为。

这些修复围绕具体错误、输入与可观察后果进行记录。Git 历史保存问题对应提交；修复前审查报告保留当时基线；当前规格与验收矩阵记录完成后的契约。

### 19.3 Codex 与 TRAE 的实际使用

项目使用 Codex 与 TRAE。使用者于 2026-11-07 确认大量使用 TRAE，具体日期、任务和截图由使用者在 [TRAE 模板](../ai-collaboration/trae-record-template.md)补充。本次 Codex 的作业核实、原始证据测试、文档整理、FauxCam 验证与提交操作记录在 [协作目录](../ai-collaboration/README.md)。

[开发提示词记录](../ai-collaboration/development-prompts.md)按实际任务保存审查、修复、同步、证据整理与相机验证的提示词、人工决定和产物。

任务约束包括现有架构、服务接口、允许修改范围、固定语料和回归要求。本次证据工作保留了修改前六项断言失败、修改后通过和完整验证。Python 检查针对缺失原文、失败运行、图片变化、重复输入和比较不一致设置拒绝条件。

人工决定负责确认实际使用情况、参考版本观察、是否采用修改和最终验收。代码变化的工具归属按照真实对话记录填写；Git 提交、测试结果和工具附件通过任务编号关联。

### 19.4 识别与解析的边界

OCR 原文可能包含近形字符、标签重复、漏字和空白变化。规则分类可能因无标签号码、组织词歧义、复杂版式和部门候选冲突产生错误。当前报告保存这些错误的实际值和计数，并提供原图、处理图、原文及初始字段。

规则采用 evidence 和阈值控制候选，无法确认的网站和部分文字留在未归类内容。Apple 上下文测试包含孤立词、姓名后的公司候选和地址中同词三种输入。字段决定需要结合实际上下文，产品通过人工确认保存最终联系人。

竖排文字、艺术字、强反光、多名片同框及真实拍照质量仍有验证限制。FauxCam 证明指定虚拟输入下的快门和回调接口流程，系统权限另有四项模拟器实际记录；物理拍摄条件未验证。
